# Как заказчик видит агентную работу — и как это совпадает с ТЗ

Это не новое ТЗ. Это то же самое, что в заметке
[«Заметка по доработке fast_plan для агентской работы»](../docs/AGENT_WORK_SCENARIO.md)
от 19 августа 2026, только сказанное живым языком: «йоу, посмотри, есть ли на тебя задача».

Ниже слова заказчика соотнесены с документом и с тем, как это должно работать в Fast Plan.

---

## 1. Что заказчик хочет одной фразой

**Чат — это диспетчер. Fast Plan — это доска передачи работы.**

В чате человеку говорят агенту: «проверь inbox».  
Агент заходит в Fast Plan **под своей учёткой**, видит задачу **на себе**, берёт её, делает коммит **в свою git-ветку**, пишет в задачу **результат от своего имени**, меняет **статус** и **исполнителя** на следующего агента.  
Следующему в чате говорят то же самое. Он видит, что задача появилась у него, читает, **кто** что написал, и продолжает.

Мессенджер внутри Fast Plan для этого **не нужен**. Нужны: учётки агентов, inbox, журнал с автором, жизненный цикл, явная передача, привязка к git.

## 2. Соотнесение слов заказчика и документа

| Слова заказчика | Где это в заметке ТЗ | Что это значит в Fast Plan |
|---|---|---|
| «У нас есть задача. У неё есть исполнитель.» | §2, §4.3, §5: задача живёт в проекте/эпике; состояние и исполнитель **не смешиваются** | Карточка Agent Ops (`DeliveryTask`): поле **исполнитель** (учётка) отдельно от **статуса** (черновик / в работе / на проверке / …) |
| «У нас есть агенты. У агентов есть свои учётные записи.» | §2 пример: Documentation / Backend / Frontend / QA / Owner; §4.1 тип «человек или агент» | Отдельный логин на каждого агента (service account). Профиль: имя, роль (`backend`, `qa`, …), тип `agent`/`human` |
| «В рамках чата говорим: посмотри, есть ли на тебя задача» | §4.5 «Мои задачи»; §8 «простая команда, не длинная инструкция» | Чат (Cursor, Telegram и т.п.) **снаружи**. Команда агенту: открыть Fast Plan → **Мои задачи**. Там только то, что назначено **на его учётку** |
| «Он залезает в Fast Plan, ага, на мне такая-то задача, приступаю» | §3.1 шаги 3–5; §7 пункты 3–4 | Inbox: новые назначения / в работе. Кнопка **взять в работу** (`claim`) → статус «В работе», исполнитель = этот агент |
| «В чате говорим: приступай. Он реализует, делает коммит в свою ветку» | §3.1 шаги 6–7: работа в **своей** git-ветке, commit, при необходимости push | Git живёт на GitHub. В задаче поля: репозиторий, **рабочая ветка агента**, список коммитов, ссылка на PR. Fast Plan не заменяет git |
| «В Fast Plan описывает результат, ставит статус и исполнителя» | §3.1 шаг 8–9; §4.2 журнал; §4.3 передача | Два действия: (1) запись в **журнал** от своей учётки; (2) **передача** — новый исполнитель + причина + что проверить дальше. Статус меняется по правилам ЖЦ, не «ручной кашей» |
| «Я бэкенд-агент, сделал коммит в ветку своего агента, задача завершена таким-то результатом, перевожу на агента тестирования» | §3.1 шаг 9; §4.3 пример «из разработки в тестирование» | Handoff: `backend` → `qa`, `to_user` = учётка QA Agent, `done_summary` = результат, ветка/SHA в полях git |
| «Идём к QA: “есть задача?” — “да, появилась”. Приступаю. Тестирует.» | §3.2; §7 пункты 6–8 | У QA в «Моих задачах» появляется эта же карточка. Он читает **журнал бэкенда** (видно автора), пишет свою запись, либо возвращает на бэкенд, либо отдаёт владельцу |
| «Комментарии привязаны к учётке. Видно, с какой учётки написано и кто писал» | §4.2: автор, дата, тип, текст; «сразу видно, кто оставил запись» | Каждая строка журнала: автор (email/имя учётки агента), время, тип (`результат` / `замечание` / `передача` / …), текст |
| «Есть какой-то жизненный цикл задач» | §5 контур статусов | Статусы: черновик → готово к назначению → назначено → в работе → на проверке → нужна доработка / готово к решению владельца → завершено (+ заблокировано). **Исполнитель при этом свой** |

Итог: устное объяснение **=** документ. Новое только акценты:

1. Чат — внешний «пинок», не объект системы.  
2. Ветка git — **ветка этого агента**, не общая `main`.  
3. Смена исполнителя — обязательный шаг передачи, а не просто правка поля втихую.

## 3. Как это реализуется (и что уже есть на ветке `feature/agent-work-handoff`)

### 3.1. Учётки агентов

На каждого агента — отдельный пользователь Fast Plan + профиль Agent Ops:

| Агент в чате | Учётка | Роль |
|---|---|---|
| Backend Agent | `agent-backend-…@agents.fastplan.local` (или свой email) | `backend` |
| QA Agent | аналогично | `qa` |
| Owner | обычный человек | `owner` |

Создание: Agent Ops → вкладка **Агенты** → service account + token.  
Токен кладётся в секрет агента. Дальше агент ходит в API/UI **как этот пользователь**.

Документ: §4.1. Код: `AgentProfile.actor_type`, `POST /api/delivery/agents/service-accounts/`.

### 3.2. Команда из чата «есть задача на тебе?»

Агент **не ищет задачу в чате**. Он:

1. Логинится (или бьёт API со своим token).
2. Открывает **Мои задачи** (`/tasks` + `GET /api/delivery/my-tasks/`).
3. Отвечает в чат: «да, #42 API claim path» или «inbox пуст».

Корзины как в §4.5: новые назначения / в работе / ждут ответа / возврат на доработку.

### 3.3. Берёт задачу и работает в git

В Fast Plan: **Claim** (или задача уже назначена на него) → статус «В работе».

В git (снаружи): ветка вида `agent/backend/42-claim-api`, коммит, push.  
В карточке задачи заполняет: `github_branch`, `github_commits`, при необходимости PR.

Документ: §3.1 шаги 6–7, §4.4.

### 3.4. Пишет результат от своей учётки

Не анонимное описание в поле задачи, а **запись журнала**:

- тип: `результат выполнения`;
- текст: что сделано, какая ветка, что проверить;
- автор = текущая учётка (видно имя/email).

Типы из §4.2:

| Тип | Когда |
|---|---|
| рабочий комментарий | по ходу |
| результат выполнения | «я сделал, вот итог» |
| передача | создаётся вместе с handoff |
| замечание проверки | QA нашёл дыру |
| блокер | не может продолжить |
| решение владельца | owner принял / вернул |

### 3.5. Переводит на следующего — это и есть «ставлю статус и исполнителя»

Заказчик говорит: «ставлю статус и исполнителя».  
В ТЗ это **одна операция передачи** (§4.3), а не два независимых клика вразнобой.

Передача содержит:

- нового исполнителя (учётка QA Agent);
- роль (`qa`);
- причину («нужна проверка claim→handoff»);
- ожидание («прогнать сценарий, вернуть или отдать owner»).

Система сама:

- пишет журнал «передача», автор = бэкенд-агент;
- ставит **предыдущего** исполнителя;
- ставит **нового** исполнителя;
- ставит статус по ЖЦ (`qa` = на проверке, возврат = `needs_rework`, owner = `ready_for_owner`).

Именно поэтому QA потом в чате честно отвечает: «да, задача появилась» — она **на его учётке**.

### 3.6. Жизненный цикл (документ §5)

```
Черновик
  → Готово к назначению
  → Назначено
  → В работе
  → На проверке          исполнитель: QA Agent
  → Нужна доработка      исполнитель: Backend Agent
  → Готово к решению владельца
  → Завершено
(+ Заблокировано)
```

Правильная картина из ТЗ, теми же словами заказчика:

- статус «на проверке», исполнитель — учётка QA;  
- статус «нужна доработка», исполнитель — учётка Backend.

## 4. Сквозной пример «как я это вижу»

```
Чат → Backend Agent: «йоу, есть задача?»
Backend → Fast Plan / Мои задачи → «да, #42»
Чат → «приступай»
Backend → claim, ветка agent/backend/42-…, commit
Backend → журнал «результат» от своей учётки
Backend → передача на QA Agent
Чат → QA Agent: «есть задача?»
QA → Мои задачи → «да, появилась #42»
QA → читает запись бэкенда (видно: писал Backend Agent)
QA → тестирует, журнал «замечание» или «результат»
QA → передача обратно на Backend  или  владельцу
Owner → открывает #42, видит всю цепочку авторов и статусов
```

Это ровно §3 + §7 заметки (минимальный сценарий приёмки).

## 5. Что не путать

| Это | Не это |
|---|---|
| Задача Agent Ops (эпик / delivery task) | Канбан-карточка или узел WBS на `/projects` — слой планирования, не inbox агента (см. §7) |
| Чат с агентом (Cursor и т.п.) | Встроенный мессенджер Fast Plan — в ТЗ §8 прямо «не нужен» |
| Передача (handoff) | Просто сменить статус, забыв исполнителя |
| Ветка агента | Коммит сразу в `main` |
| Журнал с автором | Одно общее поле «описание», которое все перезаписывают |

---

## 6. Как проверить, что «так и видно»

Если без устных пояснений следующий агент понимает: **чья задача, кто писал, что сделано, какая ветка, что делать дальше** — сценарий доведён (ТЗ §7).

Если для этого надо объяснять в чате заново — Fast Plan ещё не центр исполнения, а список карточек.

---

## 7. WBS / Kanban на `/projects` — это не inbox агента

Сейчас в Fast Plan **два контура задач**. Они могут относиться к **одному проекту**, но это **разные объекты**.

| | Планирование (`/projects`) | Исполнение агентами (`/agent-ops`, «Мои задачи») |
|---|---|---|
| Что это | WBS, Gantt, Kanban, сроки, иерархия работ | Очередь передачи: кто сейчас делает кусок, журнал, git, handoff |
| Объект | узел WBS / канбан-карточка | `DeliveryTask` (задача Agent Ops) |
| Для кого | владелец, планирование, люди в команде | Cursor / Codex / QA-агент со **своей учёткой** |
| Inbox «есть на мне задача?» | слабый: WBS, где вы проставлены assignee | основной: `GET /api/delivery/my-tasks/` |
| Журнал с автором + передача + ветка git | нет в том виде, как в ТЗ | да |

Задача агента **может висеть на проекте** Fast Plan: у `DeliveryTask` есть поле `project` (и эпик). Это не «другой мир», а **слой исполнения поверх проекта**.

Но она **не становится сама** канбан-карточкой и **не является** узлом WBS. На mind map / Gantt агент её не увидит, пока контуры явно не связать (сейчас связи с WBS нет).

Практическая схема:

1. На `/projects` — глобальный план: пакеты работ, сроки, состав продукта.
2. На `/agent-ops` — рабочие карточки агентов по этому же проекту: «сейчас бэкенд делает #42, потом QA».
3. Чат Cursor/Codex смотрит **только Agent Ops inbox**, не дерево WBS.

Связать один-в-один WBS ↔ агентскую задачу можно позже. Для сценария заказчика это не обязательно: нужна очередь исполнения, не дубль mind map.

## 8. Как подключить агентов Cursor и Codex

Fast Plan **не встраивается** в Cursor/Codex как плагин. Подключение: у каждого агента — учётка Fast Plan + API-токен; в правилах агента написано ходить в Fast Plan как в доску задач.

### 8.1. Один раз в Fast Plan

1. Включить Agent Ops (`/agent-ops`).
2. Создать проект (если ещё нет) — тот же, что на `/projects`.
3. Вкладка **Агенты** → service account на каждую роль, например Backend Agent (`backend`) для Cursor и QA Agent (`qa`) для Codex или второго Cursor.
4. Сохранить разовый токен `fp_…` и email учётки. В секреты агента, не в git.

Опционально: `allowed_project_ids` — агент видит только этот проект.

### 8.2. Что положить агенту (Cursor и Codex одинаково)

В secrets / `.env` рантайма (не в репозиторий):

```text
FAST_PLAN_BASE_URL=http://127.0.0.1:8080
FAST_PLAN_TOKEN=fp_...
FAST_PLAN_WORKSPACE_ID=1
```

В правила агента (Cursor rule / Codex instructions / `AGENTS.md`):

1. Ты — Backend Agent (или QA Agent). В Fast Plan действуешь **только этой учёткой**.
2. На «есть задача?» → `GET {BASE}/api/delivery/my-tasks/` с заголовками `Authorization: Token {FAST_PLAN_TOKEN}` и `X-Workspace-Id: {FAST_PLAN_WORKSPACE_ID}`.
3. Взять задачу → `POST /api/delivery/tasks/{id}/claim/`.
4. Код — в своей git-ветке (`agent/backend/{id}-…`), не в `main`.
5. Результат → комментарий `kind=result` + поля git на задаче.
6. Закончил → `POST /api/delivery/tasks/{id}/handoffs/` на QA / owner.

Cursor: правило в `.cursor/rules/` + секреты в окружении.  
Codex: тот же API в инструкциях агента и env рантайма.

Альтернатива без API: агент открывает UI и логинится учёткой агента. Для автопилота удобнее токен.

### 8.3. Что не является подключением

- Общая учётка владельца у всех агентов — в журнале не видно, кто писал.
- Один токен на Cursor и Codex — оба будут одним исполнителем.
- Смотреть только Kanban на `/projects` — inbox агента там нет.
